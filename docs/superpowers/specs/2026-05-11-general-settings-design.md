# 通用设置设计

**日期：** 2026-05-11

**目标：** 在现有设置层级下，将“通用设置”从占位页升级为真实二级设置页，首批支持 `主题模式`、`保持屏幕常亮`、`音量增强` 三项设置，并通过现有本地偏好体系完成持久化与页面生效。

## 背景

项目当前已经完成设置首页与二级页容器结构：

- `SettingsContainerFragment` 负责设置模块内部子页面切换
- `SettingsHomeFragment` 负责展示顶层设置入口
- `SettingsSection.GENERAL` 当前仍然指向统一占位页
- 调音设置与节拍器设置已经分别形成独立设置分支

这意味着“通用设置”的问题不再是入口缺失，而是缺少真实业务定义、持久化方案以及与现有功能页的生效约定。

当前项目中已经存在稳定的本地偏好抽象层：

- `Preferences`
- `PreferenceManager`

因此本次设计应继续复用现有偏好体系，而不是再引入新的设置存储方案。

## 推荐方案

采用与现有设置模块一致的扩展方式：

- 新增独立的 `GeneralSettingsFragment`
- 新增独立的 `GeneralSettingsViewModel`
- 新增独立的 `GeneralSettings` 数据模型
- 将“通用设置”接入现有 `Preferences` 持久化体系
- 由统一入口负责主题模式应用
- 由相关功能页在恢复显示时读取并应用“常亮”和“音量增强”配置

这样可以把改动控制在当前设置架构内，避免为三个配置项引入额外的全局事件总线或新的导航机制。

## 用户可见结构

### 设置首页入口

底部第三个标签页仍然进入设置首页，设置首页中的条目顺序保持不变：

1. `调音设置`
2. `节拍器设置`
3. `通用设置`
4. `支持与反馈`
5. `关于`

其中 `通用设置` 从占位条目升级为真实可进入的二级页入口。

设置首页中的 `通用设置` 条目应展示当前摘要信息：

- 主值：当前主题模式，显示为 `浅色`、`深色` 或 `跟随系统`
- 副值：`常亮已开启/已关闭 · 音量增强已开启/已关闭`

这样用户无需进入二级页，也能快速确认当前通用配置状态。

### 通用设置二级页

页面标题为 `通用设置`，顶部提供返回按钮，整体视觉风格与现有设置页保持一致。

页面拆分为三个设置组：

1. `主题设置`
2. `屏幕设置`
3. `音频设置`

对应控件如下：

- 主题设置：单选组，包含 `浅色`、`深色`、`跟随系统`
- 屏幕设置：开关项 `保持屏幕常亮`
- 音频设置：开关项 `音量增强`

所有设置项都采用立即保存，不提供额外的“确定”或“保存”按钮。

## 交互定义

### 主题模式

用户切换 `浅色`、`深色`、`跟随系统` 任一选项后：

- 立即保存到本地偏好
- 立即触发应用主题切换
- 返回设置首页或其他页面时，应直接看到新的主题结果

`跟随系统` 的语义固定为跟随 Android 当前系统主题，不额外引入应用自定义自动规则。

### 保持屏幕常亮

用户切换 `保持屏幕常亮` 开关后：

- 立即保存到本地偏好
- 设置页本身不要求常亮
- 需要长时间停留的核心功能页在重新显示时读取并应用该配置

首批明确覆盖的页面范围：

- 调音器页
- 节拍器页

该配置的语义是“核心功能页按需常亮”，而不是整个应用永久常亮。

### 音量增强

用户切换 `音量增强` 开关后：

- 立即保存到本地偏好
- 首批仅作用于应用内播放音
- 不作用于麦克风输入链路
- 不修改系统媒体音量
- 不跳转系统音量面板

本次明确采用的业务语义是：`播放音量放大`，即通过更响的播放参数、音色或增益策略增强应用内播放声音感知响度，而不是系统级音量破解。

首批建议覆盖的消费场景：

- 节拍器点击音
- 后续若新增提示音，也可复用同一配置

## 数据模型

### 通用设置模型

建议新增独立模型：

```kotlin
data class GeneralSettings(
    val themeMode: AppThemeMode = AppThemeMode.FOLLOW_SYSTEM,
    val keepScreenOnEnabled: Boolean = false,
    val volumeBoostEnabled: Boolean = false
)
```

### 主题模式枚举

建议新增独立枚举：

```kotlin
enum class AppThemeMode {
    LIGHT,
    DARK,
    FOLLOW_SYSTEM
}
```

默认值建议如下：

- `themeMode = FOLLOW_SYSTEM`
- `keepScreenOnEnabled = false`
- `volumeBoostEnabled = false`

主题枚举应支持从非法存储值安全回退为 `FOLLOW_SYSTEM`。

## 持久化设计

### 存储位置

继续复用现有 `Preferences` 抽象层，不新增新的存储方案。

建议新增键值：

- `generalThemeMode`
- `generalKeepScreenOnEnabled`
- `generalVolumeBoostEnabled`

建议新增接口：

- `getGeneralSettings()`
- `setGeneralThemeMode(...)`
- `setGeneralKeepScreenOnEnabled(...)`
- `setGeneralVolumeBoostEnabled(...)`

### 读取与恢复规则

持久化层需要负责防御性恢复：

- 主题模式值缺失或非法时，回退到 `FOLLOW_SYSTEM`
- 布尔值缺失时，回退到默认 `false`

这些清洗规则应集中放在模型或偏好层，不应分散到多个 Fragment 中重复处理。

## 页面架构

### GeneralSettingsFragment

新增真实的 `GeneralSettingsFragment`，替代当前“通用设置”占位页。

职责：

- 渲染三组设置项与返回按钮
- 订阅 `GeneralSettingsViewModel` 状态
- 将用户操作转发给 ViewModel
- 不直接处理偏好存储细节

### GeneralSettingsViewModel

新增独立的 `GeneralSettingsViewModel`。

职责：

- 读取当前 `GeneralSettings`
- 暴露主题单选状态
- 暴露“常亮”和“音量增强”开关状态
- 处理立即保存逻辑
- 在主题变更时触发统一的主题应用入口

不建议继续往现有 `SettingsViewModel` 中追加通用设置逻辑，避免将多个独立设置域混合到同一个 ViewModel 中。

### 设置首页摘要同步

`SettingsHomeFragment` 在页面恢复显示时重新读取当前 `GeneralSettings`，并刷新 `通用设置` 条目摘要：

- 主值：主题模式
- 副值：常亮状态与音量增强状态

这样用户从二级页返回后，可以立即看到更新结果。

### 设置内部路由

保持现有设置容器结构不变，由 `SettingsContainerFragment` 继续负责内部跳转。

建议路由规则调整为：

- `TUNER -> SettingsFragment`
- `METRONOME -> MetronomeSettingsFragment`
- `GENERAL -> GeneralSettingsFragment`
- `SUPPORT -> SettingsPlaceholderFragment`
- `ABOUT -> SettingsPlaceholderFragment`

## 生效机制

### 主题模式生效

主题模式是三项配置中唯一要求全应用立即可见生效的设置。

建议由应用级统一入口负责实际主题应用，例如通过 `AppCompatDelegate` 做映射：

- `LIGHT -> MODE_NIGHT_NO`
- `DARK -> MODE_NIGHT_YES`
- `FOLLOW_SYSTEM -> MODE_NIGHT_FOLLOW_SYSTEM`

生效时机：

1. 应用启动时读取已保存主题并应用
2. 用户在“通用设置”中切换主题后立即保存并立即应用

建议由统一入口处理实际切换行为，而不是让多个 Fragment 各自直接调用主题切换 API。

### 保持屏幕常亮生效

该配置不是全局永久常亮，而是由核心功能页在显示时按需应用。

建议首批消费页面：

- `HomeFragment` 作为调音器页
- `DetailFragment` 作为节拍器页

建议行为：

- 页面在 `onResume` 或初始化阶段读取 `keepScreenOnEnabled`
- 为 `true` 时向宿主窗口添加常亮标记
- 为 `false` 时移除常亮标记
- 页面离开时兜底清理，避免常亮影响设置页、关于页等短停留页面

### 音量增强生效

该配置首批只面向应用内播放音。

建议首批消费页面：

- `DetailFragment` 的节拍器播放逻辑

第一阶段不把“音量增强”的实现写死为某一种 DSP 或固定引擎方案，只定义抽象行为边界：

- 可以通过更响的采样资源实现
- 可以通过更高播放增益实现
- 可以通过更高感知响度的音色或包络实现

明确不做：

- 不修改系统媒体音量
- 不修改麦克风输入增益
- 不承诺突破设备物理最大音量

生效时机建议：

- 设置修改后立即保存
- 相关功能页在重新进入或恢复显示时读取并应用
- 若现有播放链路已经具备稳定的运行时刷新点，可补充为“下一拍生效”，但这不是本次设计的强制前提

## 异常与边界处理

- 偏好值损坏或缺失时，静默回退默认值，不弹错误提示
- 主题应用失败时，不应阻塞设置页继续交互
- 常亮标记应用失败时，不影响页面基本使用
- 音量增强配置即使暂时未被某页面消费，也不能导致崩溃
- 切换主题导致 Activity 或 Fragment 重建时，应保证用户仍停留在合理的设置流中，而不是被错误地甩回无关页面

## 测试策略

### 单元测试

至少覆盖以下内容：

1. `GeneralSettings` 默认值是否正确
2. `AppThemeMode` 非法值恢复是否正确
3. `Preferences` 对通用设置的读写是否正确
4. `GeneralSettingsViewModel` 是否做到立即保存
5. 切换主题或开关后，ViewModel 状态是否同步更新

### 仪器测试

至少覆盖以下内容：

1. 从设置首页点击 `通用设置` 后进入真实二级页，而不是占位页
2. 从通用设置页返回时能回到设置首页
3. 修改设置后，设置首页摘要正确刷新

### 手工验证

手工回归至少包含：

1. 切换 `浅色`、`深色`、`跟随系统`，确认主题变化正确
2. 开启常亮后进入调音器页与节拍器页，确认屏幕不会自动熄灭
3. 关闭常亮后再次进入，确认恢复正常灭屏行为
4. 开启音量增强后进入节拍器页，确认点击音使用增强后的播放策略
5. 关闭音量增强后再次进入，确认恢复普通播放策略

## 明确不做

本次设计明确不包含以下内容：

- 改写底部导航结构
- 为“支持与反馈”或“关于”补真实业务页
- 新增系统权限申请
- 跳转系统显示设置或系统声音设置页面
- 引入全局实时事件总线
- 承诺所有设备上音量增强幅度完全一致
- 扩展出更多未确认的通用设置项

## 实现摘要

本次设计在现有设置层级基础上，把“通用设置”从占位入口升级为真实设置页，并以最小范围扩展现有设置架构。主题模式负责全应用即时视觉切换；常亮与音量增强则通过核心功能页在恢复显示时读取并应用。整个方案继续复用现有偏好体系和设置容器结构，为后续继续扩展更多通用设置保留清晰边界。
