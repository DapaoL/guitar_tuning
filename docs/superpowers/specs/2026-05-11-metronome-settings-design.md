# Metronome Settings Design

**Date:** 2026-05-11

**Goal:** Add a real metronome settings page under the existing settings hierarchy. The feature must remember the last applied BPM, let users switch metronome sound type, toggle first-beat accent behavior, configure vibration feedback for accent and regular beats, and make saved settings take effect immediately.

## Context

The project already has a settings entry flow:

- `SettingsContainerFragment` hosts the settings child fragments
- `SettingsHomeFragment` shows the top-level cards
- `SettingsFragment` already implements tuner settings
- `SettingsSection.METRONOME` still routes to a placeholder page

The metronome screen itself already exists in `DetailFragment`. It supports:

- playback start and stop
- BPM input in the `30..300` range
- a ring control that adjusts BPM
- a four-beat visualizer
- a hard-coded click waveform generated by the local `MetronomeProcessor`

Today, the metronome feature has no dedicated persisted settings. BPM is stored only in the fragment instance, sound type is fixed, first-beat accent is only implied by the visualizer, and vibration feedback does not exist.

The current bottom-tab implementation in `MainActivity` replaces primary fragments when switching tabs. In practice, leaving the metronome tab destroys `DetailFragment` and stops playback. This matters for how "immediate effect" should be interpreted for settings changes made from the separate settings tab.

The app already has an established local preference abstraction in `common/data/preferences/Preferences` and `PreferenceManager`. This is the correct storage mechanism for metronome settings as well.

## Recommended Approach

Use a minimal-change extension of the current settings architecture:

- add a dedicated `MetronomeSettingsFragment`
- add a dedicated `MetronomeSettingsViewModel`
- extend the existing preference layer with metronome-specific keys and accessors
- add a `MetronomeSettings` model separate from `TunerSettings`
- update `SettingsHomeFragment` to show metronome summary values
- update `DetailFragment` so it reads and applies persisted metronome settings at startup and during playback

This keeps settings persistence and UI aligned with the existing project structure while avoiding a full metronome-engine rewrite.

## User-Facing Design

### Settings Home Entry

The settings home screen keeps the existing `Metronome` card but changes it from a placeholder entry to a real settings destination.

The metronome card should display:

- primary value: last applied BPM, for example `120 BPM`
- secondary meta: current sound type, for example `Wood Block`

This makes the top-level settings page useful even before the user enters the metronome settings detail page.

### Metronome Settings Screen Layout

The metronome settings page should follow the same visual language as the current tuner settings page:

- back button at the top
- clear page title
- vertically stacked cards or grouped sections
- immediate-save controls instead of an explicit confirm button

The content should be split into four sections.

#### 1. Default BPM

This section is display-only.

Behavior:

- shows the current remembered BPM as `120 BPM`
- shows helper copy equivalent to `Automatically remembers the last used tempo`
- does not provide a manual input field or an edit button

Definition:

- the displayed value is the last BPM that was successfully applied in `DetailFragment`
- it is not a separate fixed default chosen independently in settings

This avoids conflicting rules between a "default BPM" and a "last used BPM".

#### 2. Metronome Sound Type

This section uses a single-choice selection group with four options:

- `Wood Block`
- `Click`
- `Drum`
- `Beep`

Behavior:

- changing the selection saves immediately
- if playback is active, the new sound type starts from the next beat
- if playback is inactive, the new sound type is used the next time playback starts

#### 3. Accent Toggle

This section uses a single boolean toggle.

Copy intent:

- `Accent the first beat`

Behavior:

- when enabled, beat 1 uses accent audio behavior and accent vibration rules
- when disabled, beat 1 still remains the first beat in the four-beat sequence, but it is no longer treated as an accent beat for sound or vibration
- the beat visualizer still preserves beat order and four-step progression

Approved interpretation:

- the accent toggle affects sound and vibration only
- it does not remove beat 1 from the bar or change the fixed `4/4` structure

#### 4. Vibration Feedback

This section uses one parent toggle and two child toggles:

- parent: `Vibration feedback`
- child: `Accent beat vibration`
- child: `Regular beat vibration`

Behavior:

- the parent toggle controls whether vibration feedback is active at all
- when the parent toggle is off, both child toggles become disabled in the UI
- child toggle values are preserved while disabled
- when the parent toggle is on, the child toggles decide whether accent beats and regular beats trigger vibration independently
- if accent is disabled, beat 1 follows regular-beat vibration rules instead of accent-beat rules

This matches the approved interaction model and provides granular control without adding more advanced timing controls.

## Data Model

### Metronome Settings

Add a new settings model dedicated to the metronome:

```kotlin
data class MetronomeSettings(
    val lastBpm: Int = DEFAULT_BPM,
    val soundType: MetronomeSoundType = MetronomeSoundType.WOOD_BLOCK,
    val accentEnabled: Boolean = true,
    val vibrationEnabled: Boolean = false,
    val accentVibrationEnabled: Boolean = true,
    val regularVibrationEnabled: Boolean = false
)
```

Suggested defaults:

- `lastBpm = 120`
- `soundType = WOOD_BLOCK`
- `accentEnabled = true`
- `vibrationEnabled = false`
- `accentVibrationEnabled = true`
- `regularVibrationEnabled = false`

### Sound Type Enum

Add a dedicated enum:

```kotlin
enum class MetronomeSoundType {
    WOOD_BLOCK,
    CLICK,
    DRUM,
    BEEP
}
```

As with existing tuner enums, the enum should support safe recovery from malformed stored values.

### Playback Config

To avoid scattering raw preference values through `DetailFragment`, add a lightweight runtime config object:

```kotlin
data class MetronomePlaybackConfig(
    val bpm: Int,
    val soundType: MetronomeSoundType,
    val accentEnabled: Boolean,
    val vibrationEnabled: Boolean,
    val accentVibrationEnabled: Boolean,
    val regularVibrationEnabled: Boolean
)
```

This object does not need separate persistence. Its purpose is to group the currently active playback rules for:

- initial playback setup
- playback updates during an active session
- test assertions around accent and vibration decisions

## Persistence Design

### Storage Location

Extend the current `Preferences` abstraction instead of introducing a new storage mechanism.

Suggested new keys:

- `metronomeLastBpm`
- `metronomeSoundType`
- `metronomeAccentEnabled`
- `metronomeVibrationEnabled`
- `metronomeAccentVibrationEnabled`
- `metronomeRegularVibrationEnabled`

Suggested new accessors:

- `getMetronomeSettings()`
- `setMetronomeLastBpm(...)`
- `setMetronomeSoundType(...)`
- `setMetronomeAccentEnabled(...)`
- `setMetronomeVibrationEnabled(...)`
- `setMetronomeAccentVibrationEnabled(...)`
- `setMetronomeRegularVibrationEnabled(...)`

### Validation and Recovery

Loading rules should be defensive:

- if stored BPM is missing or outside `30..300`, fall back to `120`
- if stored sound type is missing or invalid, fall back to `WOOD_BLOCK`
- if boolean settings are missing, fall back to the documented defaults

The sanitize logic should happen inside the model or preference layer, not inside each fragment.

## Screen-Level Architecture

### Metronome Settings Fragment

Add a dedicated `MetronomeSettingsFragment` instead of reusing the placeholder page.

Responsibilities:

- render the four metronome settings sections
- bind immediate-save controls to a `MetronomeSettingsViewModel`
- reflect current saved values when the screen opens
- apply enabled and disabled UI state for the vibration child toggles

### Metronome Settings ViewModel

Add a dedicated `MetronomeSettingsViewModel`.

Responsibilities:

- load current `MetronomeSettings`
- expose UI state for sound type and toggle selections
- persist each change immediately
- expose display-ready default BPM text
- keep the vibration parent-child dependency logic out of the fragment

This avoids growing the existing tuner settings view model into a mixed-responsibility class.

### Settings Home Integration

Update `SettingsHomeFragment` so the metronome card reads current saved settings and displays:

- current last BPM
- current sound type label

The card should navigate to `MetronomeSettingsFragment` instead of a placeholder.

### Settings Section Routing

Update `SettingsSection.METRONOME` so it is treated as a real section instead of a placeholder-only section. `SettingsContainerFragment` should route it directly to `MetronomeSettingsFragment`.

## Immediate Effect Semantics

The approved behavior is immediate local persistence. In the current app structure, settings saved from the separate settings tab take effect the next time `DetailFragment` is shown, which is immediately on return because the fragment is recreated from saved preferences.

For any runtime config update that occurs while the metronome screen is active, the effect rule is next-beat application where relevant.

### Sound Type

- saving a new sound type updates local storage immediately
- returning to the metronome screen after saving uses the new sound type immediately
- if runtime config changes while playback is active, the next beat uses the new sound type without forcing a full restart

### Accent Toggle

- saving the accent toggle updates local storage immediately
- returning to the metronome screen after saving uses the new accent rule immediately
- if runtime config changes while playback is active, beat classification switches from the next beat onward
- when accent is off, beat 1 is treated as a regular beat for sound and vibration

### Vibration Settings

- saving any vibration toggle updates local storage immediately
- returning to the metronome screen after saving uses the new vibration rules immediately
- if runtime config changes while playback is active, the new vibration rules apply from the next beat
- vibration failure or lack of device support must not interrupt audio playback

### Last BPM

The settings page does not edit BPM directly.

Instead:

- whenever the user successfully applies a BPM in `DetailFragment`, that BPM is immediately saved as `lastBpm`
- the next time the metronome page opens, it initializes from `lastBpm`
- the settings home summary and metronome settings page display the new remembered value

## Detail Fragment Integration

### Initial Load

`DetailFragment` should stop hard-coding `bpm = 120` as the only startup value.

On screen entry:

- read current `MetronomeSettings`
- initialize the page BPM from `lastBpm`
- build a `MetronomePlaybackConfig`
- update BPM text, ring position, and any other relevant UI using that loaded value

### Active Playback

The current local `MetronomeProcessor` should evolve from a BPM-only generator into a processor that can honor:

- current BPM
- current sound type
- current beat index
- whether beat 1 should be treated as an accent

The implementation does not need a full audio engine rewrite. A practical first delivery can:

- keep the existing sample generation approach
- vary waveform or envelope behavior by `MetronomeSoundType`
- vary accent versus regular beat output by frequency, amplitude, or envelope shape

The metronome playback loop should also expose the current beat classification so the fragment can:

- update the visualizer
- trigger accent vibration or regular vibration
- respect accent-off behavior cleanly

### Runtime Refresh

`DetailFragment` should refresh current metronome settings in two cases:

- during `onResume()`, to pick up changes made from settings before playback starts
- whenever runtime metronome config is updated while the fragment remains active, so the next beat reflects the newest values

This can be implemented with lightweight refresh hooks. A global reactive event bus is not required for this feature.

## Vibration Design

### Device Capability Handling

Vibration should degrade gracefully:

- if the device supports vibration, use it
- if the device does not support vibration, do nothing silently
- do not block audio playback
- do not show toast errors for unsupported vibration

### Platform Compatibility

Use the Android vibration APIs behind a compatibility wrapper:

- prefer `VibratorManager` where required by platform level
- fall back to `Vibrator` on older supported versions

The wrapper should offer simple methods for:

- accent beat vibration
- regular beat vibration

The difference between accent and regular vibration can be implemented through shorter and lighter versus longer and stronger feedback. Exact waveform sophistication is not required.

## Error Handling

### Invalid or Corrupt Stored Values

The feature must recover silently by falling back to defaults when stored values cannot be parsed.

### Playback-Time Setting Changes

Playback should not restart automatically just because a setting changed. The approved rule is:

- the currently sounding beat finishes
- the next beat uses the updated configuration

This avoids abrupt transitions and reduces risk of audio glitches.

### Disabled Child Toggles

When vibration is turned off globally:

- child toggles remain visible
- child toggles become disabled
- existing values remain stored and unchanged

This preserves user intent when the parent toggle is later re-enabled.

## Testing Strategy

### Unit Tests

Add or update tests for:

1. `MetronomeSettings` default and sanitize behavior
2. `MetronomeSoundType` recovery from invalid storage values
3. preference read and write behavior for all metronome fields
4. `MetronomeSettingsViewModel` immediate-save behavior
5. vibration parent-child UI state logic
6. beat classification logic:
   - accent enabled: beat 1 uses accent rules
   - accent disabled: beat 1 uses regular rules
   - vibration disabled: no beat triggers vibration

### UI or Instrumentation Tests

At minimum, verify:

1. settings home opens metronome settings instead of the placeholder
2. changing metronome settings updates the settings home summary after navigation back
3. re-entering the metronome screen restores the last applied BPM

### Manual Verification

Manual regression should cover:

1. change BPM in the metronome screen, leave, and re-enter
2. change sound type during playback and confirm next-beat effect
3. disable accent and confirm beat 1 is no longer accented in sound or vibration
4. enable vibration parent toggle and only accent vibration
5. disable the parent vibration toggle and confirm child toggles are disabled but preserved

## Out of Scope

The following are intentionally excluded:

- changing the fixed `4/4` beat structure
- adding time-signature settings
- adding a separate metronome volume setting
- adding a preview button for auditioning sound types inside settings
- rewriting the metronome feature into a fully separate engine module
- broader navigation refactors unrelated to metronome settings

## Resolved Decisions

These decisions were explicitly confirmed during design review:

- settings must take effect immediately
- "default BPM" means the last successfully applied BPM
- BPM is not edited directly on the settings page
- vibration uses one parent toggle plus separate accent and regular child toggles
- the accent toggle affects sound and vibration only
- when accent is off, beat 1 follows regular-beat rules

## Implementation Summary

This feature adds a real metronome settings page to the existing settings hierarchy, backed by local preferences and integrated directly with the current `DetailFragment` metronome flow. The design deliberately keeps the project close to its current structure while making metronome settings persistent, visible, and behaviorally meaningful.
